- **2026-08-08** — **The dev-only annotate overlay's toggle becomes a bare `A`, the one exception to the bare-key removal.** `Ctrl+Shift+A` (the 2026-08-07 overlay) was the app's last modifier combo; the captain wanted a one-key toggle, and it is safe here where it was not on the app screens — the overlay is dev-only and never ships (dead-branch mount, bundle-gated markers), and the toggle exempts text entry, so typing the letter in any field never flips the mode. The `onKey` condition is `!ctrl && !meta && !alt && key.toLowerCase() === "a" && !isTextEntry(target)`: every modifier combo is excluded (`Ctrl+A` is select-all in any app), `Shift` is deliberately not checked so uppercase `A` toggles too, and `isTextEntry` (input/textarea/select/contentEditable, already defined for the overlay's suppression) is the same guard that makes the 2026-08-07 `lib/hotkeys.ts` removal safe. Escape and the floating button are untouched. `e2e/annotate.spec.ts`'s regression test asserts the new contract: `h`/`l`/`f`/`s` still never navigate (mode on or off), bare `a` toggles on and off, `Ctrl+A` never toggles, and typing `a` in a text input never toggles (mode on or off). The app-wide rule stands: **no other bare keys**; this overlay's `a` is the single sanctioned exception.

- **2026-08-08 (second entry)** — **Findings threshold lowered from 5 to 2 sessions; trends now carry a confidence value, and the row spells out n as sessions (UI feedback batch 5, notes 12 + 13).** The old hard gate (`MIN_TREND_SESSIONS = 5`, `robustTrend` returning INSUFFICIENT below 5) withheld a trend verdict until 5 sessions of an exercise. Now a finding appears **from 2 sessions** — `robustTrend` fits a line from 2 points (MAD outlier rejection is inherently a ≥5-point mechanism, `isOutlier` already no-ops below that, so a 2–4 point fit is a raw slope) — and the gate became a **confidence boundary instead of a withhold**: `TREND_CONFIDENCE_SESSIONS = 6`, so 2–5 sessions render as `confidence: "low"` — labeled **"Rough estimate"** on the row (amber badge, `apps/web/src/screens/findings.tsx` `TrendRow`) with a sheet caveat that says the **chance of error is high** and to keep logging — and 6+ sessions render `"medium"` (gray badge). The countdown (`CountdownFinding`) now targets 2 sessions (a 1-session exercise says "1 more session"), and the empty-state / Train-card copy says "from 2 sessions" / "Log 2 sessions". **Note 13:** the trend row's bare `n=5` is now `5 sessions` (n here is the fit n — points actually fit after MAD rejection, which equals the session count whenever no spike was dropped, i.e. always in the rough band), and every trend row shows a confidence badge; the sheet's stat line adds `· {low|medium} confidence`. Condition findings were already carrying `confidence` + `correlation, not causation`, unchanged; the condition correlation gate stays at 10 sessions (MIN_BUCKET_N × 2) — note 12 was about the trend threshold only. Recommendations are unchanged in shape and still fire on low-confidence trends, each rendering its own n — the sheet-level rough-estimate caveat covers them. The MCP `findings` tool's caveat string was updated to match. **Honest-stats posture intact**: nothing is presented as more reliable than it is — the rough-estimate label and high-error caveat *replace* the hard gate, exactly the "caveat replaces withhold" trade the captain asked for. Historical docs (2026-07-13 journey report, 2026-06-21 plan) that describe the old ≥5 gate are left as-is — they describe a past state.

The gate is on **data presence, not query status** — TanStack Query v5 keeps `data` when a *background refetch* fails and only flips `status` to error, and every bulk run ends in an `invalidateQueries(["exercises"])` whose refetch can fail, so gating on `isSuccess`/`isError` would disable the trigger (and the open dialog's submit, mid-typing) with the whole library sitting on screen. Presence is only trustworthy because **optimistic writes update the exercises cache but never create it** (`updateExerciseRows` in `queries.ts` returns `undefined` — a documented `setQueryData` no-op — when the entry is absent): the single-add path stays live during the cold load, and a `(old = [])` updater would otherwise *build* the list out of that one optimistic row and unlock bulk add against it — the exact duplicate-everything failure the gate exists to prevent. With data present the cancel is what the invalidate would have done anyway (optimistic writes update the revert state, so nothing optimistic is dropped), leaving the bulk-add path unchanged. It is **dismissable** (×) — surviving unmount otherwise means surviving the whole session, and "not retrying these" is a normal outcome; dismissing is the only thing that clears it short of the next run, so the retry prefill can't be lost by merely opening and closing the dialog. Both stores hold **per-user** state outside the query cache, so they register a reset in `apps/web/src/lib/user-scoped-state.ts` that `auth.tsx` fires next to `queryClient.clear()` on sign-out and on any user change — `clear()` doesn't reach module state, and these rows are merged back *over* server data now, so user A's pending rows and failed names would otherwise surface in user B's library on the same tab (sign-out is SPA-only; no reload). - **2026-08-07 (eighth entry)** — **iOS input-zoom fix: the existing 16px-minimum rule wasn't winning against call-site text-size classes.** Captain-reported: tapping a text input on iPhone Safari auto-zoomed the page. The codebase already carried a `@layer utilities { input, textarea, select { font-size: 16px; } }` rule (this is well-documented WebKit behavior — any focused form control resolving to a computed font-size under 16px triggers the zoom, and `user-scalable=no`/`maximum-scale=1` is the wrong fix since it also disables pinch-zoom for everyone; see https://www.smashingmagazine.com/2023/09/prevent-safari-zooming-form-inputs/ and https://css-tricks.com/16px-or-larger-text-prevents-ios-form-zoom/), but it was losing on any input carrying a Tailwind text-size utility directly (`field.tsx`'s `text-sm` = 15px, boxed `Input`/`TextField` callers passing `text-xs`, etc.) — a class selector (0,1,0) beats a bare-tag selector (0,0,1) regardless of source order within the same cascade layer, so the existing rule only ever won on inputs with no explicit text-size class. Fixed by scoping the rule to `@media (pointer: coarse)` (the actual touch/mouse distinction, not a viewport-width guess) and adding `!important`, which beats any non-important rule in the same layer regardless of specificity while leaving desktop's smaller `text-sm`/`text-xs` inputs untouched on mouse-driven pointers. The selector excludes `type="file"`/`"checkbox"`/`"radio"` — none of them takes text entry, so none can trigger the focus zoom, and forcing a font-size on them only risks resizing the control's own chrome (a file input's button label). No viewport-scale lockdown — pinch-zoom stays enabled. **Guarded automatically, with one manual step left**: `e2e/input-zoom.spec.ts` runs under the suite's default coarse-pointer profile (`e2e/playwright.config.ts` pins `devices["iPhone 13"]` on chromium) and holds the *input* to the bug — every visible text-entry control on the new-exercise sheet and on a live logging row computes to ≥ 16px, including `set-0-weight`, the `text-sm` call site the old bare-tag rule lost to — plus a `Desktop Chrome` case asserting that same input stays 15px on a mouse pointer, and a check that the viewport meta carries no `user-scalable=no`/`maximum-scale` lockdown.
